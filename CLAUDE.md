# BagelUnit Reel Kit (repo)

This folder is the kit's source, not a place to make reels.

- **"Set up the reel kit" / first time on this computer:** run `bash setup/install.sh` (Mac, Linux) or `node setup/install.mjs` (any system, including Windows) and walk the user through anything it marks as NOTE, using `SETUP.md`. Ask every question during setup (which system, whether to install a missing program, which optional parts to add, what to do next) with the AskUserQuestion tool, the question block with options and "Other", never as plain text. Never ask for, print or store an API key; the user pastes their ElevenLabs key into `~/.config/bagelunit-reels/elevenlabs.key` (Claude may make the empty file and open it, `SETUP.md` section 3).
- **Web steps go through the browser tool.** Every setup step on a website (the ElevenLabs key, the Kenney packs, Apify, Runway, and in a brand folder the Meta app, Cloudflare, Telegram, a host) is done by Claude in the user's browser with Claude in Chrome, by the rules in `template/docs/browser.md`: the user logs in, copies each secret into the file Claude made and opened, and clicks the last Delete; Claude asks before anything paid or public and never types a password or token. Early in setup, check it is on (the installer's "Browser tool" step, or `/chrome`); if not, explain it in one line (Chrome, Edge, Brave, Arc, Vivaldi or Opera; not Safari or Firefox) and ask with AskUserQuestion: turn it on now, or do the steps by hand. A project cannot switch it on, so the user runs `/chrome`.
- **After setup, the next step is always `/brand-setup`.** When the installer finishes, end by telling the user to type `/brand-setup` here. That skill (`.claude/skills/brand-setup/`) asks the brand name and where its folder goes, runs `node setup/new-brand.mjs <folder>` to copy `template/` there, then asks the brand questions and fills in that folder.
- **Point to the command.** Every next step you give names its command first: `bash setup/install.sh` (Windows `node setup/install.mjs`), `/brand-setup`, `node setup/new-brand.mjs <folder>`, then in a brand folder `/bagelunit-reels`, `/kit-update`, `/analytics-readout`. Never lead with "say ..." or "copy the folder".
- **Someone opens a session here without a clear task** (a greeting, "what now", "how does this work"): if `~/.claude/skills/bagelunit-reels/KIT.md` is missing, offer to set up the kit; if it exists, say in one or two lines that the next step is `/brand-setup` (it makes a brand folder and sets the brand up), unless they already have a brand folder, in which case they open Claude Code there.
- **Making a reel:** reels are made in a brand folder (a copy of `template/`), never here and never in `template/` itself. If the user asks for a reel here, run `/brand-setup` first (or, if they already have a brand folder, tell them to open Claude Code in it).
- **Changing the template:** after any change under `template/`, run `node setup/sync-template.mjs` (or `bash setup/sync-template.sh`) to refresh the generic copy-from folder, and tell the user that each existing brand workspace needs `node setup/sync-template.mjs <workspace>` (dry run) then `--apply`. Also run `node setup/scan-repo.mjs` before any commit. Never run it on a brand workspace without showing the dry run first.
- **Builds (every commit that changes what brands get):** `VERSION` stays the same for small builds (the owner's rule); the build stamp tells brand folders instead. After `git add`, run `node setup/stamp-build.mjs` (it writes `template/.kit-build` when `template/`, `studio/` or the install and sync scripts changed, and stages it), then commit. CI fails if the stamp does not match the files. Add what changed to the current version's CHANGELOG entry under "Added since the first release". Brand folders then hear "a newer build of X is out" at the start of a session and `/kit-update` installs it.
- **Releasing:** only when the owner asks for a new version: when a change under `template/`, `studio/`, `setup/` or the docs is worth telling people about, add an entry to `CHANGELOG.md` (plain words, newest first, no em dashes), bump `VERSION` and `template/.kit-version` to the same number (CI fails if they differ), refresh the generic folder with `bash setup/sync-template.sh`, then (after the user says to push) push, `git tag -a vX.Y.Z`, push the tag and (the release workflow does the tag and GitHub Release by itself when `VERSION` changes on main; if it fails, run `gh release create vX.Y.Z --notes-file` with that entry). Pushing and releasing are public, so only on the user's say-so.
- **Changing the engine:** `studio/` is the engine installed as `~/.claude/skills/bagelunit-reels`. Record every change to it in `studio/LOCAL-CHANGES.md`. After a change, the user re-runs `bash setup/install.sh` (or used `--link`).
- **Commands reference:** when a skill or an engine command is added, renamed or changed, update the list in `setup/make-commands.mjs` and run `node setup/make-commands.mjs --pdf` (CI fails if a command has no entry or `COMMANDS.md` is stale). Rebuild the PDF at each release so its version number is current.
- **Everything here is our own code.** Do not copy or keep outside material in the repo. Credit only the open-source parts the installer adds.
- **Docs:** `docs/process.md`, `docs/avatar.md`, `docs/sound.md`, `docs/reference.md`, `docs/dashboard-design.md` (read before changing the content dashboard's look). No em dashes in anything written here.
- **Never commit** keys, `.env` files, photos of people, avatar poses, client data, renders (except the small sample clips in `docs/samples/`), audio or `node_modules`. Never change this repo's visibility.
